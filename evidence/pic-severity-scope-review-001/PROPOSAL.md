# Four KiCad 10 severity keys: minimal routing-scope policy proposal

No production change is proposed on names alone. The smallest defensible extension separates recognized metadata, unsupported source intent, finding-critical rejection, and checks actually executed. All conclusions below refer to KiCad 10.0.0 commit `0feeca2a807f428ad2b3fa7c1e39625cb769f02c`; this review executes no native tools. Five new primary files total 97,873 bytes; ten existing cached files are hash-bound separately. Headers are retained: the two project-settings implementations are GPL-3.0-or-later, the other three new files GPL-2.0-or-later.

## Actual original intent, independently read

The unchanged 15-file original project has board version20260206, 247 pads, 63 footprints and six vias. Both Default and POWER have an explicit empty tuning_profile. The profile-definition array is empty. The complete board AST has no generated objects, backdrill, tertiary_drill, front_post_machining or back_post_machining nodes, and no text/field/dimension/table container on Edge.Cuts. No custom-rule file exists. The project does contain tuning_pattern_settings with default meander-shape preferences; these are not an active profile assignment or generated tuned route. Do not reject ordinary default preferences as if they were a hard electrical constraint. `original-intent-audit.json` binds these static observations and proves all source bytes unchanged; it does not claim native provider coverage.

## Smallest prospective native controls

Reuse the already reviewed bounded nonsaving diagnostic lifecycle, complete owned project copies, original severities, exact source/tool/argv binding, raw reports, and deliberately invalid inputs. No new framework or engine is needed. Freeze recipes before execution and retain every failure.

1. Clean owned conventional-pad/two-terminal route, full original project: establishes the positive baseline for the other cases. All new target findings absent; no other blocking/open/excluded findings. Known warnings remain recorded.
2. Change only a named nondefault class's tuning_profile to a fixed missing name in an owned project. No profile definition is added. Require actual missing_tuning_profile warning, unchanged declared severity, and diagnostic finding-critical rejection. Use a generic named class, not a PIC-specific name. A separate Default-only mutation tests the source-indicated coverage gap: retain its actual outcome without pretending omission is enforcement; the source-intent guard must reject it either way.
3. Add a uniquely identified board gr_text on Edge.Cuts; require text_on_edge_cuts error bound to that item. Independently place an equivalent footprint text/field on Edge.Cuts to exercise nested scope. Positive uses the identical text on a normal documentation layer. Raw additional outline findings may occur and must remain visible; only the exact intended finding demonstrates the provider.
4. Start from a correctly connected ordinary PTH pad and track. Add only a front counterbore post-machining node with positive diameter/depth on the track's copper side, retaining original project/stackup; require the native intent readback and track_on_post_machined_layer error bound to track plus pad. Add a separate via/backdrill case before ever claiming the via/backdrill branch. Exact parser-supported nodes are documented in `controls.json`. Connectivity membership is a real precondition: if the intended finding is absent, preserve that failure and keep the feature unsupported rather than inventing fill/geometry to force it.
5. Schematic parity stays outside the first routing-scope extension. Its eventual control needs a complete owned annotated schematic/board pair, successful explicit parity netlist loading, a matched custom-field positive and one changed/missing footprint-field negative with the exact parity finding. Running the same negative without parity is a coverage demonstration only. An empty schematic_parity array alone never proves this check ran.

The first small batch can use shared90s wall/full CPU and20MiB; the post-machining/parity branches are separate prospective batches if needed. No control should qualify until its actual native raw binding and expected failure are independently reviewed. Declared APIs are not runtime evidence; opaque getters fail rather than fall back.

## Integration boundary after controls

Use one generic, byte-bound source-intent helper from preflight, candidate validation and receipt readback, so direct routes, strategies and review-copy paths cannot bypass it. Capture source and candidate intent separately; the immutable project/board comparison remains authoritative. Add finding-critical handling through the existing central policy rather than rewriting parse_report counters or native JSON. Keep legacy receipt parsing compatible; record new explicit scope/coverage metadata outside the existing native summary dictionary. Reject unknown key values and source syntax. No filename, footprint reference, net name or UUID may confer production eligibility.

This proposal does not qualify custom pads, profile-based impedance/timing, post-machined geometry, schematic parity, imported routing transport or a four-arm comparison. The six earlier custom scenes exercise two exact Y-symmetric polygons at front0/back90 only; their outcome cannot broaden these four provider contracts.
