# Narrow support review: retained padstack warnings and unused classes

This is a read-only source investigation on the local Mac. No native KiCad process, solver, source mutation, production gate change, corpus promotion or tracked-file edit occurred. Downloaded primary-source payload totals 708,227 bytes, below the 1 MiB limit. Source review is not native qualification.

## Recommendation

A narrowly stronger acceptance policy is technically justified: preserve an original `padstack: warning` setting byte-for-byte, run the pinned native DRC with all severities, then reject any native `padstack` finding independently of its warning/error severity. A warning setting does not mean KiCad skips the check. This changes the application's acceptance threshold, not the original constraint definition or report severity. **Do not open the preflight gate until native positive and deliberately invalid warning controls pass and every final/check-result path uses that same policy.**

Limit initial support to the specifically understood padstack-warning case. Other critical warning settings, ignored checks, source exclusions, unknown severity keys, custom rules, advanced padstacks and unsupported geometry remain subject to the existing fail-closed gates. Do not rewrite project severities, promote warnings inside the raw JSON, omit checks, or invent a clean native error count.

## Acceptance policy and proof obligations

The inspected `autorouter.pipeline.parse_report` currently counts blocking findings only by `severity == error`; its excluded count looks only for severity `exclusion`. Source preflight rejects critical non-error severities, which currently blocks both target projects before this becomes a supported path. A future change must retain raw native counts, introduce a separately explained acceptance-critical finding count, and bind that count to the complete final native JSON and candidate hash. All routing, prune, review-copy, finalization and independent `check_result` paths must derive it through the same validator. Do not merely change a preflight condition.

For the narrow policy: block all existing native errors; block a `padstack` warning/error independently; block or reject explicit exclusions under the current no-exclusions scope; reject required checks in `ignored_checks`; require exact supported native version/schema/source and all-severity metadata; reject malformed or unsupported report fields/types that affect this decision. Keep every warning visible. Report native warnings as warnings and application rejection as a separate reason. Apply the same acceptance criteria to B0, B1, B2 and C in any comparison, with a new frozen protocol/version for new runs; do not rewrite historical receipts or reclassify old experiments silently.

## Native controls to run later on immutable scratch fixtures

Use a synthetic diagnostic family, not an altered production board, and retain its project with `padstack: warning` from initial creation. Include a small closed outline, two copper layers, a single ordinary SMD footprint/pad (or the existing valid smoke fixture), valid dimensions, and no exclusions. Keep source project bytes identical throughout each control. Native invocations must include zone refill/all severities and use isolated configuration under the existing bounded worker.

1. Positive: SMD pad with `F.Cu`, `F.Mask`, `F.Paste`, no hole. Require successful real native report, no `padstack` or `padstack_invalid`, no blocking findings or opens, and acceptance. Retain all independent ordinary warnings.
2. Target invalid warning: a separate fixture copy changes only that pad's paste layer to `B.Paste`, retaining front copper/mask, positive dimensions and no hole. Pinned native source predicts a `padstack` warning. Require the actual raw report to contain that exact type/severity and require the new acceptance-critical count to reject it. This must prove warning handling directly; a rejection only from changed-pad invariants, an unrelated error, or a mock report is insufficient. Also evaluate the malformed pad as the unchanged input fixture itself so source/candidate structural equality cannot mask the warning path.
3. Complement: another separate fixture uses SMD copper on both sides, which also predicts `padstack`. A distinct SMD-hole fixture predicts `padstack_invalid` and verifies the separate error type. Avoid oversized-drill-only controls as the sole proof because annular/drill errors could reject them even if warning handling were broken.
4. Preserve the existing source-hash tamper and final-report stale/corrupt controls. Pure JSON counterexamples should separately exercise missing warning severities, required ignored checks, `excluded: true`, changed report identity and unknown critical types, but these supplement the native controls. Do not mutate the original project's severity to create an ignore-case native run; an independent synthetic project or report-level rejection test suffices for that guard.

After passing those controls, run a native-only audit of the immutable-copy routed multichannel source with its original rules. Passing this narrow policy still requires checking the actual returned findings and source floors; it is not permission to route yet. Do not run the sibling unrouted project with default settings or assume its mapping is covered.

## Unused `5mil` netclass: conditional support concept only

Roller Encoder lists Default and `5mil` but no netclass patterns or explicit assignments. Its Default target dimensions are 0.1524 mm width/clearance, 0.56 mm via and 0.3 mm drill; `5mil` width/clearance are 0.127 mm. Static empty bindings do not prove native effective membership, because schematic/board class state and project attachment must be checked natively.

The [pinned DSN exporter, lines 1519–1533](https://github.com/KiCad/kicad-source-mirror/blob/0feeca2a807f428ad2b3fa7c1e39625cb769f02c/pcbnew/specctra_import_export/specctra_export.cpp#L1519) collects only in-use nondefault effective classes. [Lines 1692–1768](https://github.com/KiCad/kicad-source-mirror/blob/0feeca2a807f428ad2b3fa7c1e39625cb769f02c/pcbnew/specctra_import_export/specctra_export.cpp#L1692) export Default and the in-use classes, their native member nets, width, clearance and via choice. Thus an unused class is intentionally absent from DSN; it cannot be proved preserved by checking that DSN lists all configured classes. The original project must preserve all configured data, while the active net mapping and exported constraints must agree exactly.

A future narrow qualification may permit configured but unused classes only when the same loaded native board supplies complete effective net membership, all nets resolve to Default, the original project attachment and configured nondefault class definitions are independently observed, no assignments/patterns/directives remain unaccounted for, and pre/post source hashes prove original settings unchanged. Match native Default dimensions to original values and all minima; match every exported net/class/width/clearance/via padstack; reject loss/duplication or unexpected membership. A Default-only map is also what a missing-project load can produce, so it is not enough by itself. No DSN adapter should delete classes or rewrite settings to manufacture this case.

Required counterexamples include: a synthetic binding that makes the otherwise unused class active, a source-project-load failure, changed Default dimensions, wrong DSN membership, narrower DSN width/clearance and altered via geometry. All must fail or move into a separately qualified active-class path. Include a renaming-invariance test with another unused class identifier; do not hardcode `5mil`, filenames, or net names. Keep `text_on_edge_cuts`, B.Cu jumper behavior, exact dependencies and other unqualified settings gated until individually explained and natively exercised. No production support is proposed merely from a successful static read.
