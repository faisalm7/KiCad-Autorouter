# Six-project development acquisition audit — bounded result

The fixed-order audit acquired the selected native originals and notices for all six considered projects, including both LIS3DH variants: **35 files, 6,495,334 bytes, seven native boards**. Each original file's expected size and Git blob SHA-1 matched the pinned source tree; individual SHA-256 values are retained. The source tree was unchanged after static parsing and preflight. This is a separate development audit, not promotion into the production corpus.

New saved download payloads total **6,478,222 bytes**: 6,458,994 bytes for original project sources and two small Hardware README files, plus 19,228 bytes of dependency-license/README metadata. Another 36,340 original notice/README bytes were copied from the earlier verified metadata cache. This is below the 10 MiB batch ceiling, and every selected project is below the 10 MiB per-project ceiling. These are saved GET payload counts, not a measurement of TLS/HTTP or web-search transport overhead. No external dependency geometry, reserved holdout geometry, scripts, plugins, models, or executables were downloaded. No dataset code, native KiCad tool, engine, or solver ran.

**All seven boards are statically unsupported by the unchanged current pipeline. No project has verified complete external dependency closure. Zero independent new families or native baseline successes are claimed.** Every considered project remains in the denominator. The original files, native rules/severities/exclusions, and reference routing are untouched. Reference routing was not used as a solver solution; all seven are now development-exposed.

## Dependency closure: what is present and what is missing

Every referenced symbol `lib_id` in all seven schematics has an embedded definition. No external symbol `extends` or hierarchical sheet-file references were found. Footprint geometry and pads are embedded in the native boards and remain original. The pinned repositories contain no local footprint/symbol tables, standalone libraries, submodule pins, or exact external library revisions for these projects. No `.kicad_dru` files are listed in their complete source trees. These observations do not substitute for native project load, refill, export, DRC or schematic parity.

The boards reference external SparkFun, KiCad standard, RollerEncoder, ProtoCentral, LOGO and generated KiBuzzard library identities. Every external footprint ID and 3D model path is in `static-audit.json`. External library comparison/update is not reproducible without the correct libraries; missing library data must not be hidden by disabling checks. All 3D model references remain unresolved in this acquisition. They include old and new SparkFun directory layouts, `DROPBOX_PROJECTS`, `SPARKFUN_3DMODEL_DIR`, `SPARKFUN_KICAD_LIBRARY`, and standard KiCad model paths. SFA40 also references a private-looking absolute Windows download location from its public upstream file. That path was preserved as source data; it was not accessed or copied into a tracked document.

A full 3D and editing dependency closure cannot be inferred from the embedded 2D geometry or filled by downloading today's entire library. Models may have distinct vendor rights. We stopped without fetching an arbitrary library snapshot, relinking source references, or removing unresolved models. These sources remain incomplete for the requested full native-project corpus. The current static failures independently prevent routing qualification, so using the remaining download allowance on guessed library versions would not establish eligibility.

Original firmware, documentation images, manufacturer datasheets, rendered schematic PDF, fabrication outputs, production logs and local preference/cache files were not acquired; every omitted blob remains listed in `acquisition.json`. The native board/project/schematic originals and root licenses were retained in full. This is not a claim that root hardware grants cover third-party datasheets or models. No original rule file or native hierarchical dependency was selectively omitted to pass a check or fit the cap.

## Ancestry and coverage

The two LIS3DH sizes are one provisional family. Nine pairs of these boards share original footprint UUIDs, including VEML7700/full-size LIS3DH at 25 shared UUIDs out of the smaller 43-footprint board, and VEML7700/SFA40 at 13/41. This is direct evidence of reused template objects. It does not prove that all distinct sensor circuits are the same family, but it prevents claiming independence from repository names. `static-audit.json` records all shared pairs without changing the conservative split policy.

No baseline success or failure is measured. The earlier hypothesis that small sensor boards might provide easy baseline anchors has not been tested by a solver; instead the audit found shared source templates, missing dependency pins, nonblocking original checks, and unsupported features. These are representative corpus/support findings and remain in coverage, not reasons to replace the batch with easier boards silently. The separate prospective holdout pool was not opened or acquired.
